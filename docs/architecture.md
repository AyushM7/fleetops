# Architecture

FleetOps combines a deterministic Go simulator, Go safety/proposal lifecycle, PostgreSQL workflow persistence, authenticated GraphQL, TypeScript/Mastra reasoning and a React operator review interface. Phases 0–5 and the DEMO-01 local gateway are implemented; richer Phase 6 dashboard features and Phase 7 deployment remain future work.

## Current service and approval boundary

**LLM proposes. Go validates. Human approves. Go executes.**

[`fleet.Service`](../backend/fleet/service.go) owns the simulator and serializes snapshots, ticks, submissions and decisions with one mutex. Detached state is exposed through [GraphQL](../backend/graphql/resolver.go). The [agent tools](../agent/src/tools.ts) can read and submit a bounded proposal, but cannot approve, execute or inject faults. The host checks snapshot grounding and supported actions; Go independently controls operational admission.

An independent authenticated operator reviews canonical pending proposals. [`decision.go`](../backend/fleet/decision.go) checks runtime ownership, identity, expiry and preflight again before executing `SetCharging` or `ReassignUnstartedJob`. Proposal creation does not execute. Transfer success is distinct from delivery. [`storage.go`](../backend/fleet/storage.go) persists proposals and domain audit attempts, not running simulator state. SQL uncertainty poisons the runtime because simulator memory cannot roll back with a database transaction.

The [local demo](phase4-demo.md) uses a separate loopback gateway and deterministic reasoning adapter. Normal-server automatic ticking is optional and disabled by default; the demo scripts its own tick progression. There are no runtime dashboard lifecycle controls or playback APIs. See [Phase 5 evaluation](phase5-evaluation-report.md) and [known limitations](known-limitations.md) for evidence boundaries.

## V2 fleet identity

The V2 simulator creates ten transport robots (`R1` through `R10`) and one maintenance robot (`M1`). M1 starts in its dedicated bay at `(9, 0)`, uses the existing autonomous charging and parking rules, and is ineligible for transport assignment and reassignment. Mixed-robot tie breaks retain the order `R1` through `R10`, then `M1`. Go snapshots supply that identity to the Operations Manager, visitor status, and the event stream rendered by the Warehouse and Fleet views.

A fresh V2 runtime issues `M1` for live references, including charging reservations, occupancy, and fault reports. The runtime keeps physical state in memory and starts a fresh simulator after restart. Stored evidence, audit payloads, and historical fixtures retain the IDs recorded by their original runtime. In historical V2 evidence, `R11` identifies the maintenance robot from that runtime. Live V2 requests have no `R11` alias. V1 keeps its existing IDs and human approval workflow.

### V2 breakdowns

Motor and sensor failures stop a robot immediately with status `faulted`. Communication loss also stops it on detection and changes its status to `offline` after `UnresponsiveDelay` subsequent ticks. The active cause remains `robot_unresponsive` across that transition. Critical battery uses the existing depletion stop at zero. A healthy charging trip can still dock at zero if it reaches the station on that step. V1 keeps its existing delayed unresponsive behavior and fault records.

A stopped robot retains its cell, job assignment, and cargo custody. Its cell and occupied aisle remain obstacles. Go invalidates the executable route and releases unused charger reservations because the trip has stopped. A physically occupied dock stays occupied, and charging pauses. No tick clears an active breakdown or transfers a failed robot's job. M1 follows the same breakdown and battery rules.

The robot's optional `activeFault` gives the current cause. The `faults` list records immutable occurrences with their tick and robot ID. Incident reconciliation opens a high-severity episode from the current cause, and callers that carry the reconciliation history retain the same episode across repeated observations and offline confirmation. Fleet state reads project current incidents. The V2 event stream carries the live robot cause and occurrence history. Episode history is runtime-scoped.

Trusted Go scenarios can schedule one breakdown per robot in nondecreasing tick order. Tick zero applies at construction. Later entries apply after that tick's physical movement, in the order supplied for a shared tick. If a robot is already disabled, it keeps its first cause and occurrence. The seed controls ordinary simulation randomness. The schedule takes no random draws. The default warehouse starts with an empty schedule, and only existing physical depletion can produce a breakdown there.

Run a reproducible breakdown-only scenario from the Go module with `go run ./cmd/simrun -layout=warehouse-v2 -seed=42 -ticks=7 -repair-ticks=0 -breakdown=1:R1:motor_failure -breakdown=4:R2:robot_unresponsive`. The other supported causes are `sensor_failure` and `critical_battery`. Advancement to tick 7 confirms R2 is offline. The scenario driver is outside the visitor and model command surfaces.

### V2 physical maintenance

The Go scheduler admits a request bound to a target robot and its active fault occurrence. All breakdown episodes are high severity, so it considers the oldest occurrence first and uses robot ID for ties. It chooses the first eligible target and selects the shortest feasible orthogonally adjacent service route, using fixed neighbor order for equal distances. Service cells are clear floor outside protected aisles, narrow passages, bays, and dock approaches. M1 uses the normal movement, battery debit, and traffic reservations. Maintenance travel waits and replans within its tick budget without asking traffic recovery to displace another robot.

A preflight blocker leaves the incident open and consumes no attempt. Go reevaluates admission as conditions change. A trapped target without a legal service cell retains a `service_cell_unreachable` issue. Once dispatched, the attempt uses the occurrence's only slot, including when travel or verification times out, M1 fails, or the attempt is cancelled. A later route opening cannot redispatch that occurrence. Future AI dispatch through the same Go admission will receive `attempt_already_recorded` and must leave the incident open for other assistance. A separate breakdown occurrence has its own slot.

An assigned attempt progresses through travel, arrival, stationary repair, and verification. V2 defaults to three repair ticks at one battery unit per tick. Admission and each step budget movement, remaining work, a reachable charger or bay, and the configured battery reserve. M1 returns by the normal parking or charging path after the attempt. Motor and sensor faults can be serviced while faulted. Communications service starts after offline confirmation. Critical battery requires external power and stays open without an energy transfer. M1 can break down and is ineligible to repair itself.

Go applies scheduled breakdowns after physical movement and before advancing repair or verification. Go clears the active fault only after it validates the target and a safe, energy-feasible recovery route. An assigned job resumes toward pickup, and a collected job resumes toward its destination with the same cargo owner. Delivery completion still comes from ordinary movement. If M1 breaks, the target changes, traffic exhausts the travel budget, or verification cannot establish readiness within its budget, the simulator records the outcome and preserves the active fault when it still exists.

The optional V2 `maintenance` snapshot carries the current phase, active work, actionable blockers, and finished attempt history. Attempts refer to the immutable fault occurrence. The corresponding incident keeps its reconciliation ID until verified clearance and remains distinct from the attempt. Attempt records are simulator evidence. PostgreSQL command receipts follow the existing separate execution and persistence boundary.

Run the complete R4 delivery recovery from the Go module with `go run ./cmd/simrun -layout=warehouse-v2 -seed=42 -ticks=139 -breakdown=48:R4:sensor_failure`. Use `-repair-ticks=0` to reproduce Session 2 behavior or a positive repair duration to vary the work cost.

### Operations AI maintenance dispatch

Go continues to dispatch deterministic maintenance when no Operations decision window is active. With Operations AI enabled, an authenticated window gives the model time to choose one action while physical ticks, charging, safety, and any ongoing repair continue. A fresh eligible occurrence can start one maintenance-only review during the normal transport cooldown. Go restores deterministic admission when the window closes, AI is disabled, or the 20-tick deadline expires. Abstention, unavailable inference, timeout, invalid output, and budget denial release the window. An expired maintenance choice cannot execute even if M1 remains idle.

The model receives active breakdowns with immutable fault IDs, robot status, and live admission blockers. It sees M1 and cargo custody in the warehouse observation, recent maintenance attempts, and Go-computed options with the service cell, travel and exit steps, repair ticks, and required battery. A maintenance choice has the shape `{"kind":"maintenance","maintenance":{"robotId":"R4","faultId":"F1"}}`. The Go host retains the offered pairs, observation identity, expiry, and entity versions. The model has no tools, receives no runtime credentials, and uses the existing bounded inference and spending ledger.

The automatic command checks the active window, authenticated runtime and observation, exact offered fault pair, and versions of M1, the affected robot, and its job when assigned. It recomputes feasibility against live occupancy, energy, active fault, and attempt history before admission. The PostgreSQL command receipt confirms dispatch admission. The simulator labels AI-admitted attempts with `aiDirected`, and later simulator records establish the repair result, recovery, and delivery. Deterministic attempts retain their existing snapshot shape. A command receipt with an uncertain persistence outcome still poisons the runtime.

## Simulator

The `backend/sim` package owns validated configuration, a warehouse grid of free cells, aisles, walls, and charging stations, and the robot, job, and fault state. `New` validates and clones configuration. Robots hold integer battery percentages; jobs progress from pending through assigned and in-progress to done, retaining assignment history.

Phase 2 foundations add `WarehouseConfig`: a 20×12 grid with 104 shelf walls and three eight-cell aisles at columns 4, 9, and 14, leaving 134 eligible job cells. `DefaultConfig` retains Phase 1 geometry with AutoCharge=false; WarehouseConfig enables AutoCharge. V12 checks orthogonal connectivity through free/aisle cells and requires adjacent access for every station; station starts remain allowed, but stations cannot connect components. V13 permits at most one initial robot per aisle. V14 validates replanning, blocking, reserve battery, and enabled automatic-charge thresholds.

Ticks advance deterministically using a per-Sim seeded RNG for job generation. Pass A processes all robots in numeric ID order: decrement countdowns, apply offline expiry before other behavior, handle charging, and drain idle batteries. Pass B uses scheduler.Assign for pending jobs in numeric ID order, selecting the nearest eligible idle robot by parked-obstacle A* distance, with numeric robot IDs breaking ties. Both route legs must be reachable, and battery must meet MinAssignBattery and cover their combined movement cost plus ReserveBattery. With AutoCharge enabled, scheduler JobInfo.ExitCost also budgets the parked-obstacle distance from delivery to a currently available charging station; -1 rejects the job. AutoCharge=false uses ExitCost=0 and retains legacy behavior. A robot finishing charging is excluded for the whole tick. Pass C, when AutoCharge is enabled, selects charging trips for remaining idle robots below ChargeBelow. Pass D moves job and charging trips in numeric ID order.

Movement follows private A* routes, at most one cell per tick, with walls impassable and stations excluded from transit. Robots reject occupied cells or aisles held by another robot. Actual movement drains battery, including arrival steps; idle robots drain periodically. SetCharging requires an idle, job-free robot already at a station, checking occupied before reserved-by-another before busy/position errors. Charge is capped at 100, and completion frees the station without dispatching on that tick. Dispatch distance caches last only one pass and use map lookups without map iteration for selection.

Autonomous charging processes eligible idle, jobless robots by battery ascending, then numeric ID. Each immediately claims the nearest free reachable station by parked-obstacle A* distance, breaking ties by numeric station ID. Free means unoccupied, unreserved, and physically empty, including the candidate's own position. New trips must retain at least one battery unit on arrival. An eligible robot already on an unoccupied/unreserved station begins charging through the existing rule instead. Nonzero trips reserve the station and move with no job using existing navigation/wait/replan rules. Arrival atomically clears reservation, sets occupancy/status, and resets waiting; gain begins next tick. The existing zero-battery arrival exception remains a safety net for a pre-existing trip, not an admission budget. Depletion before arrival faults the robot and releases its reservation; offline charging occupants retain their station. Charging still runs to 100 and completion skips the rest of that tick. Queued/stranded classification is derived without new snapshot fields.

With AutoCharge enabled, ReserveBattery is the single assignment-admission contingency and must be in [5,25]. Subsequent job routes budget remaining pickup/delivery and charging exit with a floor of one battery unit, spending that contingency rather than adding it again. Relocation replacements also budget their exit; charging replacements retain one on arrival. Post-assignment exit estimates keep parked obstacles en route but ignore occupancy/reservation at the destination station, as approved for Step 1; assignment still requires a currently free station. Pickup movement is charged exactly once before planning delivery. The existing exact-zero charging-arrival safety net remains unchanged for pre-existing trips. Unaffordable replacement routes preserve the previous route, job, and reservation; waiting consumes no battery. Future legs and exits use parked-obstacle estimates and do not reserve or guarantee future station availability. AutoCharge=false retains legacy job-route behavior.

Initial pickup/delivery routes avoid offline, faulted, and charging robots and their aisles. Replanning avoids all other robots and occupied aisles, exempting the planning robot's own cell and aisle. A blocked step stays stationary without battery drain, increments waitTicks once, and replans at each ReplanAfter multiple. Successful replanning replaces the route for the next tick without resetting waiting; failed replanning retains the old route. BlockedAfter sets blocked. Movement or transition to a non-moving status clears waiting. Recovery-enabled configurations add the bounded retreat and idle-blocker clearing policies described below; these do not guarantee resolution of every traffic delay. Traffic blockage does not create fault-history records.

| Call class | Operations | Boundary |
| --- | --- | --- |
| DYNAMICS | `Tick`, including background dispatch | Background simulation, not an operator command |
| READ | `Snapshot`, `CellAt` | Snapshot owns deep copies; grid lookup is read-only |
| READ | `PlanRoute`, `AisleOccupant`, `OccupiedAislesOnRoute` | Static A* routing and physical aisle occupancy; no state mutation |
| DRIVER | `InjectLowBattery`, `InjectUnresponsive`, `InjectAisleConflict` | Trusted tests, evaluations, and scenario triggers only; never exposed to the agent |
| COMMAND | `SetCharging`, `ReassignUnstartedJob` | Operator execution requires Go validation and independent approval |

`Reader` exposes observations and previews. `Commander` embeds Reader and adds SetCharging and ReassignUnstartedJob; `Driver` embeds Reader and adds the three trusted injectors. These Go capabilities are not agent tools. Compile-time checks enforce Sim conformance. The exported-method guard requires every exported Sim method to match one of these role interfaces, except Tick; import and randomness restrictions remain enforced.

Snapshots include robot waitTicks/blocked, station reservedBy, and an ordered aisles array with zero-based IDs. Moving without a job requires enabled AutoCharge and a valid station reservation (I6); reservations must belong to charging travelers, be unique per robot, and never coexist with occupancy (I16). Aisle occupancy derives from current robot positions within the configured Y range and selects the lowest numeric robot ID if inconsistent input contains multiple occupants. Tick refreshes stored aisle records after movement; Snapshot and occupancy READs recompute without mutating state. PlanRoute adapts Config to routing.Grid, permits station endpoints, excludes station transit, and ignores robots. Route occupancy results contain distinct ascending aisle IDs whose selected occupant differs from the caller. Other traffic invariants enforce wall avoidance (I2), unique cells (I12), exclusive aisles (I13), waiting consistency (I14), and physical occupancy snapshots (I15).

Background dispatch remains simulator dynamics, separate from operator commands under the frozen safety rules. The implemented fleet service serializes access to the non-goroutine-safe Sim. Agent access uses authenticated GraphQL, never direct simulator imports.

Unresponsive countdowns run before other robot behavior, even while faulted. Expiry makes the robot offline, overriding faulted without another movement, drain, or charging step. Offline robots retain their jobs and occupied stations, while interrupted charge trips release reservations. Status transitions, scheduling, and autonomous charging create no fault records; successful trusted injections do.
