# P4-03 operator-approved reassignment

`ReassignUnstartedJob(jobId, fromRobotId, toRobotId)` transfers ownership of an
assigned, uncollected job from a currently traffic-blocked source to a healthy
idle recipient. It does not remove the obstruction or promise delivery.
Execution `succeeded` means transfer succeeded; subsequent ticks perform pickup
and delivery using the existing navigation and recovery behavior.

Go checks both robots exist, are available and have battery >=30%, distinct
identities, source ownership and `assigned` job status, source not already at
pickup, source blocked condition, recipient idle/jobless and not reserved for
charging, and no duplicate ownership. Pending unresponsive injections are also
unavailable. Admission uses existing A* with all other robots' current cells and
occupied aisles blocked for pickup, delivery and exit to a free charger. Recipient
energy must cover every leg plus the configured reserve and assignment minimum.
The pickup route installed by the command is the admitted route.

The existing service mutex serializes ticks, previews, submission, approval and
execution. Preflight runs at creation, approval and immediately before execution;
the command checks its own physical preconditions again. An independent operator
must approve. Rejection, expiry and denied preflight do not execute. Duplicate
decisions cannot replay a command. Every attempt uses the existing PostgreSQL
audit path. Persistence uncertainty poisons the runtime and requires manual
reconciliation, even when a transfer already occurred.

## Read and submit through GraphQL

All queries require authentication. Viewer/proposer/operator may read. The jobs,
incidents and candidates are from one locked live snapshot. Candidates are
admission evidence only and do not reserve a robot, route or charger.

```graphql
query {
  fleetState {
    tick poisoned
    robots { id x y battery status jobId waitTicks blocked }
    activeIncidents { robotId type severity }
    jobs { id status assignedRobot fromX fromY toX toY }
    reassignmentCandidates {
      jobId fromRobotId toRobotId
      pickupSteps deliverySteps chargingExitSteps requiredBattery
    }
  }
}
mutation Submit($input: ReassignUnstartedJobInput!) {
  submitReassignment(input: $input) {
    proposalId state execution executionAttempted auditCommitted error
  }
}
# variables: use current Go candidate IDs and a future RFC3339 expiresAt.
```

Use the proposer credential for submission. Then, with a separate operator
credential, inspect `pendingProposals { id action jobId fromRobotId toRobotId
expiresAt submittedBy currentRuntime }` and call the existing
`approveProposal(id: ...)` or `rejectProposal(id: ...)` mutation. No Tick,
Commander, Driver or injection mutation exists. In proposal reads, the charging
fields `robotId`/`stationId` are empty for reassignment; `jobId`/`fromRobotId`/
`toRobotId` are empty for charging. Always branch on `action`. The React dashboard
is not updated in this ticket and is not the reassignment review surface.

## Agent

Use Node.js **24.21.0**. Existing private `.env` settings supply the endpoint and
proposer token. No new dependencies or provider setup is required.

```powershell
cd agent
npm run build
npm start
npm start -- --submit
```

Offline mode deterministically selects the first Go candidate (job/robot numeric
order), or retains the existing in-place charging behavior. The first invocation
only recommends. `--submit` permits at most one submission attempt. Host code
reads and validates a fresh complete snapshot immediately before submission and
refuses changed/unavailable evidence; Go revalidates under its lock when handling
the mutation and again at approval/execution.

Optional live reasoning retains P4-02's explicit `--live` and provider-key gates;
paid requests remain disabled by default. Read the provider/cost setup in
README before enabling it. No live provider requests are part of this ticket's
tests. The model receives only snapshot facts, references and the supported
candidate; credentials and private environment configuration remain in the host.
Only `readFleetState` is in the model tool map. Reassignment reasoning must copy
the exact job, source, recipient, Go candidate, current tick and source
`traffic_blocked` reference. Host validation rejects mismatches or unsupported
commands. Incident references are snapshot-scoped `(tick, robotId, type)`, not
stable IDs and not valid across simulator runs.

## Deterministic full demonstration

```powershell
cd agent
npm test
npm run typecheck
pwsh -NoProfile -ExecutionPolicy Bypass -File scripts/verify-integration.ps1
```

The harness requires Docker and the existing Go toolchain, starts its own
PostgreSQL 18.6 container, applies migrations and tests isolated schemas, and
cleans up its server/container. It runs all Go packages with the race detector
and `-tags fleetops_test`, then the real backend agent tests and Node/Mastra
contract checks. The test tag enables trusted fixture construction only in test
builds; normal production builds omit it. There is no runtime recovery-demo
switch or GraphQL injection endpoint.
The existing `make test-integration` target also enables this test-only tag, so
the Go recovery/approval tests run in the existing integration CI job.

Stage 1's private test fixture starts R1 with J1 before pickup and an offline
robot at its pocket's only exit. Automatic dispatch, navigation, charging and
recovery all remain enabled. At tick 42 R1 is healthy, battery 100, wait 42 and
blocked. The identical baseline is observed for another 200 ticks (66 replanning
opportunities, over 13 recovery thresholds); the obstruction remains and J1 is
still assigned at tick 242. A test-only counterfactual uses the existing scheduler
to admit R3, which delivers at tick 45. Every tick checks simulator invariants.

Stage 2 replays that scenario through real GraphQL submission and independent
approval. A local deterministic provider adapter exercises actual Mastra
generation, output validation and optional proposal submission. The simulator
does not change before approval. Approval atomically clears R1 and assigns R3;
normal ticks complete delivery while the identical baseline remains blocked.
Separate cases demonstrate rejection, expiry, stale requests, authorization,
duplicate decisions, and fail-closed failed/uncertain database commits.

Migration `004_reassign_unstarted_job.sql` replaces only the action constraint
with a two-action allowlist. Existing JSON payloads and SetCharging history remain
unchanged; no simulator/job persistence or incident IDs are added. Apply it
forward with the existing migration runner before running the updated service.
